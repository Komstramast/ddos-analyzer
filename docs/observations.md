## 2026-09-16 — Захват трафика

### Первый запуск сниффера: что поймали
- **Фильтр:** `ip`
- **Проблема:** захвачен только multicast-шум.
- **Что видно:** mDNS (224.0.0.251:5353), NetBIOS (10.241.255.255:138), LLMNR (224.0.0.252:5355), IGMP (224.0.0.22).
- **Вывод:** в сети с Windows-машинами фоновая multicast-активность доминирует. Нужен более узкий фильтр.

### Проблема с определением интерфейса
- Scapy по умолчанию выбирал разные адаптеры между запусками.
- Один из GUID, выбранных автоматически, был от VirtualBox или VPN.
- **Решение:** явное указание интерфейса в `config.py` через MAC-адрес.

### Обнаружение фоновой активности Dr.Web
- **Процесс:** `dwnetfilter.exe` (PID 11180)
- **Путь:** `C:\Program Files\DrWeb\dwnetfilter.exe`
- **Поведение:** десятки одновременных TCP-соединений на порт **8886** к разным серверам.
- **Примеры IP:** 185.162.130.x, 162.244.34.x, 2a07:b400::x
- **Назначение:** облачная проверка URL и репутации (Dr.Web Net filtering service).
- **Классификация:** легитимный трафик антивируса.
- **Решение:** исключён фильтром `not port 8886`.

**Ценность для ВКР:** пример легитимного трафика, по паттерну похожего на DDoS (много коротких TCP-сессий к одному порту). Позже будет использоваться как тест на ложные срабатывания.

### Финальный рабочий фильтр 
(tcp or udp port 53 or icmp) and not port 8886


### Захвачен нормальный трафик
- **Файл:** `data/normal_traffic.pcap`
- **Содержимое:** DNS-запросы, HTTPS-сессии (TCP/443), TLS handshake с Яндексом.
- **Анализ в Wireshark:**
  - Фильтр `udp.port == 53 or tcp.port == 443`.
  - Виден полный TLS 1.2 handshake: SYN → SYN/ACK → ACK → Client Hello → Server Hello → Server Key Exchange → Client Key Exchange → Encrypted Handshake → Application Data.
  - DNS: запросы AAAA-записей к `suggest.sso.dzen.ru`, ответы от роутера.

### Статистика нормального трафика
| Параметр | Значение |
|---|---|
| Длительность сессии | ~2 секунды (200 пакетов) |
| PPS в покое | 0–10 |
| PPS при сёрфинге | 20–300 |
| BPS при сёрфинге | 0.5–300 KB/s |
| Доля DNS | ~70% в «тихие» моменты |
| Доля TCP/443 | ~30% |
| Доля SYN в норме | 0–22% (пики при открытии новых соединений) |
| Максимальный размер пакета | 2239 байт |
| Средний размер пакета | ~150 байт |

## 2026-09-16 — Этап A: агрегация метрик и детекция

### Что реализовано
- Потокобезопасный агрегатор метрик (PPS, BPS, доля SYN, топ-источники, топ-UDP-порты).
- Периодический сброс и вывод сводки раз в секунду.
- Три правила детекции:
  - `HIGH_PPS` — PPS от одного IP > 300.
  - `SYN_FLOOD` — доля SYN среди TCP > 70% при TCP >= 10.
  - `UDP_FLOOD` — PPS UDP на один порт > 400.
- Запись метрик и алертов в SQLite (`data/traffic.db`).
- Время в БД — локальное (исправлено с UTC на `datetime('now', 'localtime')`).

- Классификация: ложное срабатывание.

### Ключевой вывод по этапу A

**Порог PPS=300 срабатывает на легитимный трафик.** Все три алерта — ложные.
Причины:
1. Низкий порог для домашней сети, где 300 PPS — норма при просмотре видео.
2. Правило смотрит только на PPS, игнорируя BPS, длительность, репутацию IP.

**Направления улучшения (для следующих итераций):**
- Учитывать BPS вместе с PPS.
- Требовать устойчивости аномалии N секунд подряд, а не одной секунды.
- Различать «один источник → один пункт назначения» (DDoS) и «один источник → много пунктов» (CDN/браузер).
- Исключать известные CDN по списку подсетей.

## Открытые вопросы

1. **Почему IP `8.47.69.0` регулярно появляется в топ-источниках?** Адрес оканчивается на `.0` — обычно это сетевой адрес, а не хост. Возможно, артефакт разбора Scapy.
2. **Нужно ли фильтровать IPv6?** Сейчас фильтр `(tcp or udp port 53 or icmp)` ловит и IPv6-трафик. Пока не мешает, но надо решить, обрабатывать его или исключать.
3. **Как влияет Wi-Fi на метрики?** Ретрансмиссии в беспроводной сети могут искажать PPS/BPS.
