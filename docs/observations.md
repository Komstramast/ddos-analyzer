## Этап 1. Настройка окружения и захват трафика

### Проблемы и решения
- **Npcap.** Установлен в режиме WinPcap-compatible. Без этой опции Scapy не видит интерфейсы.
- **Аутентификация Git.** GitHub не принимает пароль по HTTPS. Настроен SSH-ключ.
- **Запуск от админа.** Для захвата пакетов на Windows PowerShell должен быть запущен от имени администратора.

### Структура проекта
Создан модульный скелет: `capture/`, `analysis/`, `storage/`, `web/`, `tests/`, `data/`.

### Первый запуск сниффера: что поймали
- **Фильтр:** `ip`
- **Проблема:** захвачен только multicast-шум.
- **Что видно:** mDNS (`224.0.0.251:5353`), NetBIOS (`<broadcast>:138`), LLMNR (`224.0.0.252:5355`), IGMP (`224.0.0.22`).
- **Вывод:** в сети с Windows-машинами фоновая multicast-активность доминирует. Нужен более узкий фильтр.

### Проблема с определением интерфейса
- Scapy по умолчанию выбирал разные адаптеры между запусками.
- Один из GUID, выбранных автоматически, был от VirtualBox или VPN-клиента.
- **Решение:** явное указание интерфейса в `config.py` через MAC-адрес.

### Обнаружение фоновой активности антивируса
- **Процесс:** `<процесс-антивируса>` (облачный фильтр сетевого трафика).
- **Поведение:** десятки одновременных TCP-соединений на порт **8886** к разным серверам.
- **Назначение:** облачная проверка URL и репутации соединений.
- **Классификация:** легитимный трафик.
- **Решение:** исключён фильтром `not port 8886`.

**Ценность для ВКР:** пример легитимного трафика, по паттерну похожего на DDoS (много коротких TCP-сессий к одному порту). Позже будет использоваться как тест на ложные срабатывания.

### Финальный рабочий фильтр
`(tcp or udp port 53 or icmp) and not port 8886`

### Захвачен нормальный трафик
- **Файл:** `data/normal_traffic.pcap`
- **Содержимое:** DNS-запросы, HTTPS-сессии (TCP/443), TLS handshake с публичным веб-ресурсом.
- **Анализ в Wireshark:**
  - Фильтр `udp.port == 53 or tcp.port == 443`.
  - Виден полный TLS 1.2 handshake: SYN → SYN/ACK → ACK → Client Hello → Server Hello → Server Key Exchange → Client Key Exchange → Encrypted Handshake → Application Data.
  - DNS: запросы AAAA-записей, ответы от локального DNS-резолвера.

### Статистика нормального трафика
| Параметр | Значение |
|---|---|
| Длительность сессии | ~2 секунды (200 пакетов) |
| PPS в покое | 0–10 |
| PPS при сёрфинге | 20–300 |
| BPS при сёрфинге | 0.5–300 KB/s |
| Доля DNS | ~70% в «тихие» моменты |

- Потокобезопасный агрегатор метрик (PPS, BPS, доля SYN, топ-источники, топ-UDP-порты).
- Периодический сброс и вывод сводки раз в секунду.

## Этап 6. Улучшение правила SYN_FLOOD (Этап B)

**Проблема (обнаружена в перепрогоне v2):** правило SYN_FLOOD не срабатывало, потому что SYN-ratio считался по всему TCP-трафику. Хост отвечает RST/ACK на каждый SYN-пакет, из-за чего общий SYN-ratio падал до 50–65% вместо 90%+. Порог 70% не достигался. False Negative.

**Решение:** SYN-ratio теперь считается по каждому источнику отдельно. Правило SYN_FLOOD использует `top_syn_ratio` — долю SYN от самого активного по SYN источника. Жертва (хост) в этом счётчике не участвует, потому что она не шлёт SYN-пакеты.

**Результат перепрогона v3 (исправленный детектор):**
- Алертов `SYN_FLOOD`: **14** (было 0 в v2).
- `top_syn_ratio` в пике: **100%**.
- `top_syn_ip`: `192.168.56.101` (атакующий).
- Первый алерт `SYN_FLOOD` пришёл при PPS всего 35.
- Общий SYN-ratio при этом оставался 50% (правильно).
- Пиковый PPS: 4463.
- Дамп сохранён как `data/syn_flood_v2-1.pcap`.

**Вывод для ВКР:** агрегированный показатель (SYN-ratio по всему трафику) не всегда отражает атаку. Распределение по источникам точнее и устойчивее. Это конкретное улучшение, которое можно описать в главе 3 как «вторую итерацию».

## Технические проблемы и находки, выявленные в экспериментах

- **Scapy `sniff()` на Windows** не реагирует на Ctrl+C, пока не получит следующий пакет. *Решение:* заменён на `AsyncSniffer` — работает в фоновом потоке, главный поток спит и мгновенно обрабатывает прерывание.
- **Windows loopback для TCP:** полноценные TCP-соединения к локальному адресу хоста обрабатываются через loopback и не видны Npcap на Host-Only адаптере. *Решение:* перевернуть схему эксперимента (атакующий — хост, цель — VM).
