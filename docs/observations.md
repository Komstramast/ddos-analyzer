## Дата 2 — Захват трафика

### Первый запуск сниффера: что поймали
- **Фильтр:** `ip`
- **Проблема:** захвачен только multicast-шум.
- **Что видно:** mDNS (`224.0.0.251:5353`), NetBIOS (`<broadcast>:138`), LLMNR (`224.0.0.252:5355`), IGMP (`224.0.0.22`).
- **Вывод:** в сети с Windows-машинами фоновая multicast-активность доминирует. Нужен более узкий фильтр.

### Проблема с определением интерфейса
- Scapy по умолчанию выбирал разные адаптеры между запусками.
- Один из GUID, выбранных автоматически, был от VirtualBox или VPN-клиента.
- **Решение:** явное указание интерфейса в `config.py` через MAC-адрес.

### Обнаружение фоновой активности антивируса
- **Процесс:** `<процесс-антивируса>` (облачный фильтр сетевого трафика).
- **Поведение:** десятки одновременных TCP-соединений на порт **8886** к разным серверам.
- **Назначение:** облачная проверка URL и репутации соединений.
- **Классификация:** легитимный трафик.
- **Решение:** исключён фильтром `not port 8886`.

**Ценность для ВКР:** пример легитимного трафика, по паттерну похожего на DDoS (много коротких TCP-сессий к одному порту). Позже будет использоваться как тест на ложные срабатывания.

### Финальный рабочий фильтр
(tcp or udp port 53 or icmp) and not port 8886

- **Содержимое:** DNS-запросы, HTTPS-сессии (TCP/443), TLS handshake с публичным веб-ресурсом.

## Дата 3 — Этап A: агрегация метрик и детекция

### Что реализовано
- Потокобезопасный агрегатор метрик (PPS, BPS, доля SYN, топ-источники, топ-UDP-порты).
- Периодический сброс и вывод сводки раз в секунду.
- Три правила детекции:
  - `HIGH_PPS` — PPS от одного IP > 300.
  - `SYN_FLOOD` — доля SYN среди TCP > 70% при TCP >= 10.

- Запись метрик и алертов в SQLite (`data/traffic.db`).
- Время в БД — локальное (исправлено с UTC на `datetime('now', 'localtime')`).

- Классификация: ложное срабатывание.

### Ключевой вывод по этапу A

**Порог PPS=300 срабатывает на легитимный трафик.** Все три алерта — ложные.
Причины:
1. Низкий порог для домашней сети, где 300 PPS — норма при просмотре видео.
2. Правило смотрит только на PPS, игнорируя BPS, длительность, репутацию IP.

**Направления улучшения (для следующих итераций):**
- Учитывать BPS вместе с PPS.
- Требовать устойчивости аномалии N секунд подряд, а не одной секунды.
- Различать «один источник → один пункт назначения» (DDoS) и «один источник → много пунктов» (CDN/браузер).
- Исключать известные CDN по списку подсетей.

### Этап B — Улучшение правила SYN_FLOOD

**Проблема (обнаружена в перепрогоне v2):** правило SYN_FLOOD не срабатывало,
потому что SYN-ratio считался по всему TCP-трафику. Хост отвечает RST/ACK
на каждый SYN-пакет, из-за чего общий SYN-ratio падал до 50–65% вместо 90%+.
Порог 70% не достигался. False Negative.

**Решение:** SYN-ratio теперь считается по каждому источнику отдельно.
Правило SYN_FLOOD использует `top_syn_ratio` — долю SYN от самого активного
по SYN источника. Жертва (хост) в этом счётчике не участвует, потому что
она не шлёт SYN-пакеты.

**Результат перепрогона (v3):**
- Алертов SYN_FLOOD: **14** (было 0 в v2)
- `top_syn_ratio` в пике: **100%**
- `top_syn_ip`: `192.168.56.101` (атакующий)
- Первый алерт SYN_FLOOD пришёл при PPS всего 35
- Общий SYN-ratio при этом оставался 50% (правильно)
- Пиковый PPS: 4463

**Вывод для ВКР:** агрегированный показатель (SYN-ratio по всему трафику)
не всегда отражает атаку. Распределение по источникам точнее и устойчивее.
Это конкретное улучшение, которое можно описать в главе 3 как «вторую итерацию».

### HTTP-flood (Python-скрипт, 30 сек, 50 потоков, target=http://192.168.56.101:5000/)

**Важно:** схема перевёрнута — атакующий хост (192.168.56.1), цель Flask в Kali (192.168.56.101).
Причина: Windows сворачивает полноценные TCP-соединения через loopback, если цель — хост.
Обратное направление видно Npcap без проблем.

- Всего запросов: 8591, средний RPS: 286.4
- Пиковый общий PPS: 4279
- Пиковый BPS: 395 KB/s

  - HIGH_PPS: ~28

Это **ограничение порогового подхода** — детектор не может отличить
HTTP-flood от легитимного высокого трафика на прикладном уровне.
